## For Developers

### Translation System Architecture

The I18N system uses **per-language YAML files** to maintain translations and a Python script to generate C++ code:

```
lib/I18n/
├── translations/                # One YAML file per language
│   ├── english.yaml
│   ├── spanish.yaml
│   ├── french.yaml
│   └── ...
├── legacy/                      # Key orders of past releases' slots (i18n_legacy_layout.py)
├── I18n.h
├── I18n.cpp
├── LangPack.h / .cpp            # The card pack format and its reader
├── LangPackConvert.h / .cpp     # The conversion of a 2.40 or 2.41RC slot
├── I18nKeys.h                   # Enums (auto-generated)
├── I18nStrings.h                # String array declarations (auto-generated)
└── I18nStrings.cpp              # English, key hashes, past layouts (auto-generated)

assets/sd-fonts/Language-<Name>/<code>.cplang   # One pack per language but English (gen_i18n.py --packs)

scripts/
├── gen_i18n.py                  # Code and pack generator
└── i18n_legacy_layout.py        # Records a past release's slot layout
```

**Key principle:** All translations are managed in the YAML files under `lib/I18n/translations/`. The Python script generates the C++ code (English and the tables) at every build, and the packs on the card when asked to.

### Generation runs on every build

`scripts/gen_i18n.py` is a PlatformIO `pre:` script (`extra_scripts` in `platformio.ini`). Every `pio run` calls it with `strip_unused=True`, so the generated files are always current and keys that no source file references are left out. The three generated files (`I18nKeys.h`, `I18nStrings.h`, `I18nStrings.cpp`) are git-ignored; do not commit them.

The script skips the work and prints `Unchanged: all I18n outputs are up to date.` when every output is newer than every YAML file, the script itself and the `lib/I18n/legacy/` files.

The build never writes the language packs: `python3 scripts/gen_i18n.py --packs assets/sd-fonts` does (see
[Adding a New Language](#adding-a-new-language)). When the committed packs no longer hold what the YAML files say, the
build prints `WARNING: N language pack(s) in assets/sd-fonts differ from the YAML files` and the packs to rewrite.

You normally never run it yourself. If you want to check a translation file without a full build, run it by hand **with `--strip-unused`**:

```bash
python3 scripts/gen_i18n.py --strip-unused
```

Without that flag the output keeps every unused key and is about 31 KB bigger. The next build then finds the outputs up to date and skips regeneration, so the bloat ships. If you ran it without the flag, run it again with `--strip-unused --force`.

| Option                | Meaning                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------- |
| `translations_dir`, `output_dir` | Optional positional arguments. Defaults: `lib/I18n/translations` and `lib/I18n/`    |
| `--strip-unused`      | Omit `STR_*` keys that no scanned source file references. The build always does this          |
| `--src-dirs DIR...`   | Directories scanned for `STR_*` uses. Default: `src lib`                                      |
| `--force`, `-f`       | Regenerate even when the outputs are up to date                                               |
| `--verbose`, `-v`     | Print per-key info and warnings and the files written                                         |
| `--packs DIR`         | Write every language's pack but English's into `DIR/Language-<Name>/` instead, only those that changed |

### YAML File Format

Each language has its own file in `lib/I18n/translations/` (e.g. `spanish.yaml`).

A file looks like this:

```yaml
_language_name: "Español"
_language_code: "ES"
_order: "1"

STR_CROSSPOINT: "Witch Reader"
STR_BOOTING: "BOOTING"
STR_BROWSE_FILES: "Buscar archivos"
```

**Metadata keys** (prefixed with `_`):
- `_language_name` — Native display name shown to the user (e.g. "Français")
- `_language_code` — C++ enum name (e.g. "FR"). Please use the [ISO Code](https://en.wikipedia.org/wiki/List_of_ISO_639_language_codes) of the language. Must be a valid C++ identifier.
- `_order` — Controls the position in the Language enum (English is always 0)

**Rules:**
- Use UTF-8 encoding
- Every line must follow the format: `KEY: "value"`
- Keys must be valid C++ identifiers (uppercase, starts with STR_)
- Keys must be unique within a file
- String values must be quoted
- Use `\n` for newlines, `\\` for literal backslashes, `\"` for literal quotes inside values

### Adding New Strings

To add a new translatable string:

#### 1. Edit the English YAML file

Add the key to `lib/I18n/translations/english.yaml`:

```yaml
STR_MY_NEW_STRING: "My New String"
```

Then add translations in each language file. If a key is missing from a
language file, the generator will automatically use the English text as a
fallback (and print a warning). A translation reaches the reader through its
language's pack: rewrite the packs (`gen_i18n.py --packs assets/sd-fonts`) and
the manifests, as in [Adding a New Language](#3-write-its-pack).

A key's meaning and its `printf` arguments are fixed for its name: a pack on
the card serves every firmware from 2.41 on, older ones included. A string that
formats other arguments needs a new key (see [The pack format](#the-pack-format)).

#### 2. Build

The next build runs the generator for you (see [Generation runs on every build](#generation-runs-on-every-build)). It:
- Fills missing translations from English
- Updates the `StrId` enum in `I18nKeys.h`
- Regenerates English and the key hashes in `I18nStrings.cpp`

#### 3. Use in code

```cpp
#include <I18n.h>

// Using the tr() macro (recommended)
renderer.drawText(font, x, y, tr(STR_MY_NEW_STRING));

// Using I18N.get() directly
const char* text = I18N.get(StrId::STR_MY_NEW_STRING);
```

**That's it!** No manual array synchronization needed.

### Adding a New Language

A language is a YAML file in the repository and a pack on the card. The example uses Greek, which is not shipped.

#### 1. Create a new YAML file

Create `lib/I18n/translations/greek.yaml`. Give it an `_order` no other file uses (the shipped files run from 0 to 26,
so the next free one is 27); the generator reports duplicates. `_language_code` names the pack's file in lower case
(`el.cplang`), and `_language_name` is what the language picker shows, in the language's own script:

```yaml
_language_name: "Ελληνικά"
_language_code: "EL"
_order: "27"

STR_CROSSPOINT: "Witch Reader"
STR_BOOTING: "ΕΚΚΙΝΗΣΗ"
```

You only need to include the strings you have translations for. Missing keys fall back to English automatically.

#### 2. Build

The next build regenerates the code: the language joins the `Language` enum and the picker, by its name. The image
gains its code and name, nothing more; the strings go to the card.

#### 3. Write its pack

```bash
python3 scripts/gen_i18n.py --packs assets/sd-fonts
```

writes `assets/sd-fonts/Language-Greek/el.cplang` (the folder is named after the YAML file: `portuguese_br.yaml` gives
`Language-PortugueseBR`) and rewrites any other pack whose YAML file changed. Then list it in
`lib/EpdFont/scripts/sd-fonts.yaml`, beside the other `Language-` entries:

```yaml
  - name: Language-Greek
    description: "Menus and messages in Greek"
    format: language
    inDownloadAll: false
```

and regenerate the manifests the Font Manager reads (the command reproduces the committed `fonts.json` and
`fonts-v3.json` when nothing changed):

```bash
python3 scripts/generate-font-manifest.py --input assets/sd-fonts \
    --base-url "https://raw.githubusercontent.com/jpirnay/witchhunt-reader/master/assets/sd-fonts/" \
    --output assets/sd-fonts/fonts.json --output-v3 assets/sd-fonts/fonts-v3.json \
    --config lib/EpdFont/scripts/sd-fonts.yaml
```

Commit the YAML file, the pack, the `sd-fonts.yaml` entry and both manifests. The packs on master serve every firmware
from 2.41 on, so a new language reaches a firmware that knows its code (step 2) as soon as master has its pack. To try
it without a download, copy the pack to `/.crosspoint/lang/` on the card and pick the language.

#### 4. Glyphs

The generator refuses a translation that uses a character no UI font can draw, and lists each one
(`CRITICAL: translation(s) use characters no UI font can draw`). A missing glyph draws nothing, so
the alternative is a label with a silent hole in it. Greek would stop here: the UI faces do not carry
the Greek block, so `0x0370,0x03FF` has to go into `UI_LANG_INTERVALS` in
`lib/EpdFont/scripts/convert-builtin-fonts.sh` first, and the faces regenerated. "Can draw" means
every UI face has the character: the three Inter sizes in both weights and Noto Sans 8
(`lib/EpdFont/scripts/ui_font_coverage.py`).

### Chinese, Japanese and Korean

Their characters are not in the Inter faces, and all of CJK is tens of thousands of glyphs. So each of
the three translations gets its own small UI face per size, holding exactly the characters that
translation uses: `lib/EpdFont/builtinFonts/cjk_ui_{zh,ja,ko}_{10,12}.h`, 1-bit like the Inter faces,
cut from the Noto Sans CJK region of the language (the region picks the glyph forms, which differ for
many shared Han characters). `src/CjkUiFonts.cpp` attaches them behind every UI face as fallback
glyphs, all three whatever the UI language, because the language picker draws each language's name
in its own script.

The faces ship compressed, as 2 KB DEFLATE groups (`compress_ui_face.py`, which transforms the
generated header and never re-renders a glyph). UI screens do not prewarm a glyph cache, and a glyph
decoded on its own costs ~1.9 ms on the X3, so a Chinese Settings page decoded that way would add
~135 ms to every draw. The active UI language's two faces are therefore inflated into its language
pack slot, after its strings (see below), and drawn from there like an uncompressed face. Only the
other two languages' glyphs decode per glyph, through `FontDecompressor`: the language picker's names
and CJK book titles.

- **Changing a CJK translation** usually adds characters. Regenerate its faces with
  `python lib/EpdFont/scripts/build_cjk_ui_fonts.py` (it downloads the three Noto Sans CJK OTFs,
  ~16 MB each, on first use); the build fails until you do.
- **Sizes**: `CJK_UI_FONT_SIZES` in `lib/EpdFont/scripts/font-sizes.sh`, 10 and 12 pt. A UI face takes
  the largest CJK size not above its own: 8 and 10 pt UI text draws CJK at 10 pt, 12 and 14 pt at 12 pt.
  A 14 pt CJK size would cost ~125 KB more, for the large UI step alone.
- **Cost**: 97,132 B of flash for the compressed faces of all three languages (175,916 B flat; zh
  599, ja 500, ko 442 glyphs at the time of writing), their strings on the card like every other
  language's, and ~1.5 KB of RAM: the attached copies of the UI faces' tables, the two providers, and
  the two face tables that point into the language pack slot. Why the faces stay in the image while
  the strings left it: [below](#what-a-cjk-pack-carries-besides-its-strings).
- **The font preview sample** (`STR_FONT_PREVIEW_SAMPLE`) stays English in the three files: the font
  selector draws it in the reader font being previewed, not in a UI face, and the built-in reader
  fonts have no CJK. The glyph check cannot see that, because it checks against the UI faces.
- **Line breaks**: wrapped UI text (`GfxRenderer::wrappedText`) also breaks between Chinese and
  Japanese characters, by the reader's CJK line-break rules (kinsoku included). Korean breaks at its
  spaces.
- **Not covered**: anything that is not a UI string. A Chinese book title draws the characters it
  shares with the translations and a box (□) for each of the rest; titles need the reader's CJK font
  as a further fallback (`docs/future_work/cjk.md`). Every CJK face carries that box, and a CJK
  character no face has draws as it rather than as nothing. There is no CJK keyboard, and bold UI
  text draws CJK in the regular weight.

### I18N API Reference

```cpp
// === Convenience Macros (Recommended) ===

// tr(id) - Get translated string without StrId:: prefix
const char* text = tr(STR_SETTINGS_TITLE);
renderer.drawText(font, x, y, tr(STR_BROWSE_FILES));
Serial.printf("Status: %s\n", tr(STR_CONNECTED));

// I18N - Shorthand for I18n::getInstance()
I18N.setLanguage(Language::ES);
Language lang = I18N.getLanguage();

// === Full API ===

// Get the singleton instance
I18n& instance = I18n::getInstance();

// Get translated string (three equivalent ways)
const char* text = tr(STR_SETTINGS_TITLE);              // Macro (recommended)
const char* text = I18N.get(StrId::STR_SETTINGS_TITLE);   // Direct call
const char* text = I18N[StrId::STR_SETTINGS_TITLE];       // Operator overload

// Set language
I18N.setLanguage(Language::ES);

// Get current language
Language lang = I18N.getLanguage();

// Save language setting to file
I18N.saveSettings();

// Load language setting from file
I18N.loadSettings();

// Get character set for font subsetting (static method)
const char* chars = I18n::getCharacterSet(Language::FR);
```

## How the strings reach the screen

For most of this firmware's life every language sat in the app image as
`const` data, and `I18n::get()` returned a pointer straight into it. That cost
**408,668 B** for 24 languages, of which any one reader uses one. Deflate packs
in the image brought it to ~195 KB for 26. Since 2.41 the image carries English
alone, and every other language is a file on the SD card:

| | where it lives | cost |
| --- | --- | --- |
| **English** | app image, uncompressed, with its offset table | ~17 KB |
| **The key hashes** | app image: a 32-bit hash per key and the keys in hash order | ~6 B a key, ~5.4 KB |
| **Every other language** | `/.crosspoint/lang/<code>.cplang` on the card, 11–15 KB each | 0 B of the image |
| **The active language** | unpacked from its card pack into the tail of the `spiffs` partition, read by `mmap` | 0 B of RAM |

The packs ship like the hyphenation packs: `assets/sd-fonts/Language-<Name>/` in
the repository, listed in `fonts-v3.json` with `"format": "language"`, installed
by the Font Manager or the web font page into `/.crosspoint/lang/`, or copied
there by hand.

### Why not just decompress into RAM

Because ~30 KB resident, on a device whose steady-state free heap at the Home
screen is under 40 KB, is not affordable. An `mmap`'d flash pointer reads
exactly like the `const` data it replaces, so `I18n::get()` stays a few loads
and an add and nothing is retained.

### The pack format

`lib/I18n/LangPack.h` has the layout. A 64 B header (magic `CPLG`, format 1, the
language code in lower case, the native name, the entry count, and the CRC32
and lengths of the payload and of an optional extension), then a raw deflate
payload of entries `[u32 key hash][UTF-8 value, NUL]`.

**A pack names its strings by key, not by index.** The hash is FNV-1a of the
key's name (`STR_SETTINGS_TITLE`), so a pack does not depend on the StrId order
of any firmware: the pack on master serves every firmware from 2.41 on. A key
the firmware does not know is skipped; a key the pack lacks reads as English,
and so does a value equal to English, which the generator leaves out.
`gen_i18n.py` fails the build when two key names hash alike, over every key and
every key of the past releases below: rename one of them.

Because one pack serves many firmwares, **a key's meaning and its `printf`
arguments are fixed for its name.** A string that changes what it formats (a
`%s` that becomes a `%d`, a second `%s`) needs a new key, or an older firmware
formats the new text with the old arguments.

The window is **4 KB** (`DEFLATE_WINDOW_BITS = 12` in `gen_i18n.py`), and
`FlashLangPartition::INFLATE_RING_BYTES` must match it. A 32 KB window would
save a few KB on the card and cost eight times the transient RAM to unpack a
pack, which is the wrong trade here.

### What happens on the device

`I18n::refreshActiveStrings()` runs when the language is loaded at boot and
whenever it changes. It opens the language's pack and reads its 64 B header,
nothing more, and asks `FlashLangPartition::acquire()` for the slot under a
**stamp**: a CRC over the pack's payload CRC, its extension, and
`KEY_LAYOUT_STAMP`, the CRC of the firmware's key hashes in StrId order. If the
slot holds that stamp, it is mapped and the card is not read further. Otherwise
it is rebuilt, which happens when the language changes, when the pack on the
card changes, and when a firmware update adds, removes or reorders keys (an
update that does not keeps the slot):

1. erase as much of the slot as the pack's inflated payload can need;
2. inflate the payload from the card through a 4 KB ring, find each hash in
   `KEYS_BY_HASH` (a binary search over the generated table) and write the
   string of every key the firmware has, recording its offset in a table indexed
   by StrId; a key the pack has no string for keeps `FALLBACK` (0x8000);
3. write the table, then the extension (below);
4. write the header last, so an interrupted build reads as absent rather than
   as corrupt.

`I18n::get()` reads `STRINGS_EN_DATA + OFFSETS_EN[id]` for a `FALLBACK` entry,
so the slot depends on the key order and on nothing of the English text.

Transient RAM while a pack builds: 5 KB of scratch (the ring, a 512 B block of
the card and 256 B of inflate output), the 512 B write chunk, the table
(~1.8 KB) and the inflate's state (~1.3 KB). Nothing is kept afterwards.

**Any failure falls back to English** rather than to blank rows: no pack on the
card, a pack of another language or format, a payload that does not match its
CRC or its lengths, a slot that cannot be written. The Home screen and the
language picker then offer the pack (`UiLanguagePacks`, `PackOffer`).

**The slot proves its contents before anything reads them.** The header
carries a CRC32 of the strings and table, and one of the extension, both taken
from the bytes as `build()` wrote them, and `map()` checks both before it hands
out a pointer. A header alone is not proof: other firmware writes this flash.
A firmware from before the 128 KB slot keeps its 64 KB slot in this slot's upper
half and its font cache below that, so going back to one and forward again can
leave this header standing over bytes it did not write. On the X3 that drew
the Chinese 12 pt face as solid boxes. Now a slot that fails its CRC is rebuilt
at once, in the same boot, and mapped again: one rebuild per refresh at most,
so a slot that cannot be written right costs one rebuild, never a loop. The
check reads what the slot holds once per map: 88,264 B for Chinese, ~20-30 KB for
most languages: ~10.7 ms for Chinese on the X3 (`slot_crc` in `env:bench_font`).

### Updating from 2.40 or 2.41RC

The slot survives a firmware update. 2.40 and 2.41RC unpacked the selected
language into it from a pack in their image: one string per StrId of their own,
in their order, with no key names. 2.40 wrote a 32 B format-1 header in the
partition's last 64 KB, 2.41RC a 40 B format-2 header at the slot's place.

When the selected language has no pack on the card, `I18n::convertLegacySlot()`
looks for such a slot, format 2 first, and converts it:

- **Which release wrote it** is told by the slot's format and key count alone
  (2.40: 870 keys, 2.41RC: 878). `scripts/i18n_legacy_layout.py <tag>` runs the
  tag's own generator over the tag's tree, as that release's build did, and
  writes the key order and the Language order to `lib/I18n/legacy/<tag>.keys`;
  `gen_i18n.py` turns each into `LEGACY_LAYOUTS`, a table of this build's StrIds
  (~1.7 KB a release). Two releases whose slots share a format and a key count
  but not an order cannot be told apart: the generator leaves both out.
- **It must hold the selected language**, by the release's Language order, and
  hold together: `langpack::oldSlotSound()` repeats the walk the old table was
  derived by (every entry where the table says, empty where it said English,
  one per key and no more), and a format-2 slot must pass its CRC.
- **It is written to the card** as `/.crosspoint/lang/<code>.cplang`, through a
  `.tmp` file renamed into place: the payload as stored deflate blocks, since the
  image has no deflate encoder (a few KB larger than the Font Manager's). The
  slot is then built from that pack like any other, and the next update finds it
  on the card.
- **Once.** The first slot this firmware builds retires a 2.40 slot it did not
  reach (`FlashLangPartition::build()` erases its header sector); 2.41RC's lay
  where the new one is built. A pack removed from the card later reads as
  missing, not as the old firmware's strings again.
- **Not converted**: a slot of an unknown release, of another language, a CJK
  language's 2.41RC slot (its UI faces came from that release's image), or a
  card that refuses the file. The reader then sees English and the offer.

To let a later release's readers keep their language the same way, add its tag:
`python3 scripts/i18n_legacy_layout.py <tag>` and commit the `.keys` file. Only
a release that wrote an index-based slot needs one; from 2.41 on, the card holds
the pack.

### What a CJK pack carries besides its strings

An *extension*: bytes written after the strings, built, erased and mapped with
them (`FlashLangPartition::Extension`, registered through
`I18n::setPackExtension()`). Chinese, Japanese and Korean keep their two CJK UI
faces there, inflated from the compressed faces in the image: per size, the flat
bitmap and its offset table, exactly what an uncompressed face carries.

- **The stamp** mixes in the faces' CRCs, so new font data rebuilds the slot as
  new strings do.
- **The rebuild** adds the faces' inflate, ~0.21 s for Chinese on the X3 (105 ms
  a face), and the erase and writes of 88 KB: a switch to Chinese takes ~0.9 s,
  ~0.7 s more than with a strings-only pack. Each face is checked against the
  CRC32 its header states before the slot is trusted.
- **If the extension fails** (it does not fit, a face does not inflate to its
  CRC, a write fails, it fails the slot's CRC even after a rebuild), the strings
  stand alone and the faces decode per glyph: slower, not wrong. The next
  refresh tries again. If the slot cannot be mapped with the faces, the strings
  are mapped alone, and nothing is rebuilt for it.
- **Sizes**: Chinese needs 88,264 B of the slot and Japanese 78,504 B, so they
  map two 64 KB pages; Korean, at 63,508 B, still fits one, as does every other
  language.

**The faces stay in the image** (97,132 B compressed) while the strings moved to
the card. The flat bitmap the slot holds is only half a face: its glyph table
and intervals are in the image, so a pack that carried the bitmap would fit
exactly one firmware's glyph set, and the pack on master would draw boxes on
every firmware cut before the faces were last regenerated. The image faces also
draw the three languages' names in the language picker, whatever pack is
installed, and the CJK book titles their characters cover in every UI language.
Moving them takes a self-describing face in the pack (glyph table, intervals and
bitmap) and a small built-in face for the picker's names:
`docs/future_work/cjk-ui-faces-on-card.md`.

### Where the slot lives

The last 128 KB of the `spiffs` partition, which is not a filesystem here — it
is the flash font cache (`FlashFontPartition`) and the TTF glyph store. Both stop
short of the reservation: `beginWrite()` erases and budgets only up to
`fontUsableSize()`, an index reaching past the ceiling is treated as invalid so
the font cache re-derives from the `.cpfont` files on the SD card, and the glyph
store rejects a layout past its region and installs again. The slot was 64 KB
until the CJK UI faces moved into it; the 64 KB more came out of the font cache,
which migrates itself that way on the first boot after the change.

### The verification you get for free

`gen_i18n.py` reads every pack back as it writes it, the way the device does
(inflate at the real window size, the entries by hash), and raises if any string
does not come back identical. The host tests read a generated pack through the
device code (`test/i18n_lang_pack`), and convert a German slot built the way
2.40 and 2.41RC built theirs, back to the same German by this build's StrIds. A
format mistake fails the build instead of shipping as a screen full of wrong
text.

## File Storage

Language settings are stored in:
```
/.crosspoint/language.bin
```

This file contains:
- Version byte
- Current language selection (1 byte)

The packs of every language but English are on the card, in `/.crosspoint/lang/` (`de.cplang` and so on). The
unpacked strings of the active language live in flash — see the section above.

## Translation Workflow

### For Developers (Adding Features)

1. Add new strings to `lib/I18n/translations/english.yaml`
2. Build (the generator runs as part of it)
3. Use the new `StrId` in your code
4. Request translations from translators, and once they are in, rewrite the packs and the manifests
   (`gen_i18n.py --packs assets/sd-fonts`, then `generate-font-manifest.py`)

### For Translators

1. Open the YAML file for your language in `lib/I18n/translations/`
2. Add or update translations using the format `STR_KEY: "translated text"`
3. Keep translations concise (E-ink space constraints)
4. Make sure the file is in UTF-8 encoding
5. Run `python3 scripts/gen_i18n.py --strip-unused --force` to verify the file generates, or just build
6. Run `python3 scripts/gen_i18n.py --packs assets/sd-fonts` to write your language's pack; to try it, copy it to
   `/.crosspoint/lang/` on the card
7. Test on device or submit for review
